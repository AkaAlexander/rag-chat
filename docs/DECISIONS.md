# Technical decisions

| Choice | Reason | Alternative and trade-off |
|---|---|---|
| Next.js App Router, React and Tailwind | One project serves the interface and HTTP routes. Strict TypeScript makes contracts traceable from the chat to the provider. | A separate API service could scale ingestion and manage its lifecycle independently. |
| UTF-8 Markdown and plain text | Both preserve the original passages for citations. The 256 KiB limit bounds the work for each upload. | PDF support would require text extraction, OCR for scanned pages and checks for reading order and page references. |
| SQLite, better-sqlite3 and JSON vectors | A local file is easy to inspect during a demo. Transactions and a unique content digest prevent partial writes and duplicate content. | PostgreSQL with pgvector supports shared access and vector indexes. The current search reads every chunk, so latency and memory use matter as the corpus grows. |
| Local multilingual MiniLM | Documents and questions share a vector space across English, Spanish and Dutch. Cached weights remove repeated downloads. | A hosted embedding service reduces local computation and introduces usage costs and text transfer. Changing the model requires reindexing. |
| 80-unit windows with 16 units of overlap | Overlap retains context near boundaries. Fixed windows are easy to reproduce and test. | Splitting by heading, table row or model token might preserve long clauses and table headers more reliably. |
| Cosine filtering followed by lexical scoring | Cosine captures paraphrases. Rare terms help distinguish moving-house leave from other kinds of leave. The 0.35 cosine threshold applies before reranking. | An independent lexical search could recover passages below the threshold. Compare relevant-passage recall and latency on a larger corpus. |
| Four chunks per search and one optional follow-up | This bounds context size while allowing a more specific query. The second round adds only new passages. | A single search reduces latency. More rounds may help with compound questions but require extra calls and a stopping rule. |
| Ollama, OpenAI and Anthropic adapters | The RAG flow uses the same structured-generation and tool-call operations across providers. Ollama uses local HTTP and the hosted adapters use their SDKs. | A single provider would simplify implementation. Each selected model must support its adapter’s output schema and tools. |
| Zod validation and numbered source IDs | The server checks types and references before showing an answer. Excerpts come from the index. Confidence is the model’s own estimate. | Immediate token streaming reduces perceived latency but can expose an unverified reference. Human review can identify unsupported claims even when citation IDs are valid. |
| Delimited context and server-side configuration | The prompt separates question, history and potentially hostile excerpts. Keys come from the environment. Prompt instructions mitigate injection risks within the limits of model behavior. | A multi-user library would require authentication and document-level authorization. Multiple server instances would also need a shared rate limiter. |
| Vitest and a live in-memory evaluation | Simulated responses exercise contracts and search limits. Fifteen live questions exercise the production answer flow against known documents. | Human assessment or a larger corpus could better measure paraphrases, contradictions and open-ended answers. |

The recorded Ollama run scored 14/15 on answers, 11/12 on citations and 3/3 on abstentions. One request failed and succeeded when repeated in isolation. The complete-run metrics retain the failure. [Evaluation results](../evals/RESULTS.md)
